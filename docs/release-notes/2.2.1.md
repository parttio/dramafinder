# DramaFinder 2.2.1

DramaFinder 2.2.1 makes `getText()` leave out tooltips, so a component reports
the same text a `withText(..)` query found it by, and adds a getter for the
accessible name a `withAccessibleName(..)` query matches. Label lookups find a
field by its `FormLayout` item label, Grid header lookups read column captions
under a header group row, a row click works on a grid inside a template and on
a card that fills its cell, and the wait after an action covers a server-side
navigation and a page whose Flow UI has not started yet.

## Upgrading from 2.2.0

No source changes are needed. Three behaviours differ:

- **`VaadinElement.getText()` leaves out tooltips** (#301). A tooltip set with
  `setTooltipText(..)` is a `vaadin-tooltip` child of the component it
  describes, and `getText()` used to return its text with the component's own:

  ```java
  Button save = new Button("Save");
  save.setTooltipText("Saves the form");
  ```

  ```java
  ButtonElement button = find(page, ButtonElement.class).withText("Save").single();
  button.getText();        // 2.2.0: "SaveSaves the form"   2.2.1: "Save"
  button.getTooltipText(); // "Saves the form"
  ```

  The text of every `vaadin-tooltip` inside the component is left out, at any
  depth, so a card or layout holding a button with a tooltip no longer reports
  that tooltip either. Everything else stays: slotted text such as a card's
  title or a prefix, and the text of child components. Whitespace is still
  returned as the DOM holds it. A test that asserted the concatenated text now
  fails; assert the component's text and the tooltip separately.

  `getText()` returns an empty string for a component without text, never
  `null`.

  Elements that read a narrower text keep doing so: `BadgeElement`,
  `TooltipElement`, `MarkdownElement` and `GridElement.CellElement` override
  `getText()` and are unchanged.

- **Grid header lookups read column captions under a header group row**
  (#299). On a grid with a group row above the captions
  (`prependHeaderRow().join(..)`), `findHeaderCell(column)`,
  `findHeaderCellByText(text)` and the lookups built on them
  (`findCell(row, caption)`, `RowElement.getCell(caption)`,
  `assertHeaderCell`, `assertColumnPresent` / `assertColumnNotPresent`) used to
  read the group row; they now read each column's caption, the cell holding
  its sorter:

  ```java
  grid.prependHeaderRow().join(firstName, lastName).setText("Name");
  ```

  ```java
  grid.findHeaderCell(1).orElseThrow().getText(); // 2.2.0: "Name"   2.2.1: "Last Name"
  ```

  To reach the group cell, pass its row: `findHeaderCell(0, column)` /
  `findHeaderCellByText(0, "Name")`. Those now resolve the cell through the
  column, so a column after a joined cell gets its own cell, and a joined cell
  reports the first column it spans. Grids with one header row are unchanged,
  and so is `getHeaderCellContents()`, which still reads the first header row.

- **A row click lands on the cell's centre first** (#298).
  `RowElement.click()`, `doubleClick()`, `select()` / `deselect()` and the
  grid-level `select(int)` / `deselect(int)` used to click the middle of the
  cell's left padding; they now click the cell's centre when it is free of
  interactive content, as a user does, else the free spot nearest it. A click
  listener on a plain element in the cell (a card's `div`, a `Span`) now
  fires, as it does for a user; a link, button or field in the cell is still
  not clicked. A test that relied on the click missing such a listener now
  sees it fire.

## New

- **`GridElement.getColumnCaptions()`** (#299) returns each visible column's
  caption: its own header text or, when that is blank, the nearest column
  group's text above it. See
  [GridElement](../specifications/GridElement.md#headers).


- **`getAccessibleName()` and `assertAccessibleName(..)`** on every element
  (#302) read the name `withAccessibleName(..)` matches: `aria-labelledby`,
  `aria-label` or a native label on the component or its own input; a
  button's, tab's or badge's own text when it has no `aria-label`; a tooltip's
  text. `null` means the component has no name. Unlike `getAriaLabel()`, a
  field named by its visible label reports that label:

  ```java
  TextFieldElement.getById(page, "name").getAccessibleName(); // "Name", from new TextField("Name")
  ButtonElement.getById(page, "close").assertAccessibleName("Close"); // icon button, setAriaLabel("Close")
  ```

  See [VaadinElement](../specifications/VaadinElement.md#accessible-name).

- **A field is found by its `FormLayout` item label** (#303). A field added
  with `addFormItem(field, "Email")` has no label of its own; `withLabel(..)`,
  `withLabelContaining(..)` and every `getByLabel` factory now match it by the
  form item's label. A field's own label still wins, and a field nested inside
  the wrapped component (the text field of a custom field) is not named by the
  item. `FormLayoutElement.getFieldByItemLabel(..)` returns the field of the
  item with that exact label, whatever its type:

  ```java
  TextFieldElement email = TextFieldElement.getByLabel(page, "Email"); // addFormItem(new TextField(), "Email")
  Locator field = formLayout.getFieldByItemLabel("Email");
  ```

  See [FormLayoutElement](../specifications/FormLayoutElement.md).

## Fixes

- **A row click works on a grid inside a template and on an app's element
  covering the cell** (#298). The click spot was hit-tested from the document,
  which answers the template's host for a grid in a Lit template's shadow
  root, so every row was refused with *"the row has no data cell with a spot
  free of interactive content"*; it is now hit-tested from the grid's own
  root. An app's own element (not `vaadin-*`) with an open shadow root no
  longer counts as interactive as a whole: the click is followed into its
  shadow root and judged by what it lands on there. A `vaadin-*` component and
  a custom element with a closed shadow root still count as interactive. See
  [GridElement](../specifications/GridElement.md#how-a-row-gets-selected).

- **The wait after an action covers a server-side navigation** (#304). When a
  listener calls `ui.navigate(..)`, Flow (React mode, Vaadin's default) updates
  the address bar only after it has handled the response, so the wait could
  return with the old URL. It now also waits for the navigation, at most two
  seconds, so a read of `page.url()` right after the action sees the new path.
- **The wait after an action that loads a page lets Flow start first** (#305).
  Flow registers the view's UI only after the page's `load` event, and the
  idle check answered idle in that gap, so a read right after a login form
  post, a link out of the view or `Page.setLocation` could see an empty page.
  The wait now lets Flow start the UI, then waits for it to go idle. A page
  without Flow is idle at once; a page that runs Flow but shows no Flow UI (a
  Hilla view) waits at most 3 seconds, once per page load.

  Both waits honour the opt-out (`AutoWait.withoutWaiting(..)`,
  `-Ddramafinder.autoWait=false`). See
  [Actions and waiting](../guide/actions-and-waiting.md#navigation-waits-too).

## Documentation

- `docs/specifications/VaadinElement.md` and the `getText()` Javadoc say what
  the method reads, and how that differs from browserless tests: there, Flow's
  `Element.getText()` reads only a component's own text nodes, so
  `new Div(new Span("Hello"))` reads `""` server-side and `"Hello"` in the
  browser.
